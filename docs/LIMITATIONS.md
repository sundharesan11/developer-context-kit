# Limitations

Linux support is not claimed. CI run 38154524118 at commit `8f1133a` (2026-10-11) passed the suite and acceptance on Ubuntu 24.04 and on the Node 22.13.0 floor. Those remain evaluation lanes until support is deliberately adopted and reviewed. Windows is unsupported. Client-data migration is not implemented; `live migrate` only moves a live setup made under the old devctx name ([MIGRATING.md](MIGRATING.md)). There is no sync, and a backup needs a folder that you approve. Without a backup, a lost laptop can expose local data if disk protection is inadequate and can lose the only copy.

This pilot supports multi-record onboarding, with one registry publication point and crash/replay tests. The checks do not prove behavior against a malicious same-user process, real agent routing, live accounts, legal redistributability, or production readiness. The synthetic harness defers `fresh-agent-smoke`; fresh-agent checks belong to live activation.

Live mode is implemented; see [LIVE.md](LIVE.md). The owner's first activation on one real machine passed on 2026-10-25 at `b95ff72`, including fresh non-interactive Claude and Codex sessions. Interactive sessions have not yet been checked, and that is one machine and one repository, not broad compatibility. Live mode writes only `devtwin-*` entries directly inside the two named skill folders. It never repairs, adopts or chmods foreign entries or folders, and never writes `~/.codex/skills`. The approved config digest catches accidental edits, not deliberate same-user tampering. Skill-builder and skill-source installs stay pilot-only. The live store has a backup only after you approve a backup folder ([Backup and restore](LIVE.md#backup-and-restore)). Without a backup, losing `~/.devtwin` loses every record, journal and piece of evidence, and leaves installed skills unowned. Onboarding copies some client repository text into the store. It is protected only by the store's 0700 mode and the disk's encryption.

Onboarding stores every Git remote of the repository in the project binding as evidence, including remotes behind candidates the owner did not accept. A brief can therefore show a remote that belongs to another organization. Remotes are evidence, not identity, and nothing routes accounts by them today. Planned organization identity routing must not treat a stored remote as proof of which organization owns the project.

The skill builder has deterministic workspace, format and disposable-installation tools. Its conversational `SKILL.md` and live-model behavior evaluation are deferred. Validation does not run generated helpers or prove that a skill asks good questions. B's tests prove file, approval and recovery guards only; they do not prove discovery, routing, fresh-session behavior or real-home readiness. The validator intentionally accepts a strict frontmatter subset described in [SKILL-BUILDER.md](SKILL-BUILDER.md). Skill-package export and publication remain unavailable.

The [personal harness layer](HARNESS.md) is evaluated with synthetic fixtures only. How a live model behaves with `devtwin-setup` or a template-made skill is not evaluated, and fresh-session discovery of either is not verified. `devtwin-setup` is not yet in the bundled installer, and installing a template-made skill into a real agent home is not available in this stage. The personal profile is protected only by file modes and the same-user boundary. The announcement watch and the radar run in live mode only under the `stackWatch` exception, and live requests are always unauthenticated, so GitHub allows roughly 60 of them an hour. The bundled stack catalog covers eight items through GitHub releases and package or lifecycle identifiers, plus seven radar sources. Two of the radar sources are vendor model deprecation pages, read only for model IDs and retirement dates. The catalog lists no vendor changelog feed, so feeds are added with `--feed`. The deprecation extractor reads table rows only. If a vendor page loads its table with a script, moves or redirects, that source fails and reports no retirements. The tests use fixture pages. The two page URLs and the extractor were checked by hand against the live pages on 2026-10-27. Radar ranking uses your stack and stated interests only; package names that are in a project but not in your profile stack do not rank. The radar jobs use macOS launchd and `osascript`; on other systems the jobs cannot be installed and notifications are not shown. The monthly review reminder counts waiting preference and lesson proposals only, until the setup review (P6) lands. Relevance is whole-word term matching: it can miss announcements that use other words and can match unrelated ones. Nothing reads or sends Slack messages, and drafts saved with `draft save` cannot be sent later.

Portable selected-record handoff is a separate private Markdown feature, described in [HANDOFF.md](HANDOFF.md). It holds URL-bearing or absolute-path text, including leading-slash route literals, and fails on final packet overflow. It does not establish confidentiality, historical filesystem state, application tests, legal rights or readiness to share. Only the exporting worktree is observed; a documentation snapshot is not an application clone. Existing absolute-path records are not rewritten. Re-onboarding retires earlier auto-created profiles of the same worktree by default (see [ONBOARDING.md](ONBOARDING.md)), but profiles kept with `--keep-previous` or created from other worktrees stay effective. Interrupted writes are non-atomic and invalid-footer artifacts must not be used. Distribution, import and synchronization remain separate work.

Third-party acquisition stages an explicit bounded file selection only. It does not infer package roots, dependency trees, generated bundles, optional extensions, licenses to redistribute, native-host support or installation recipes. A selected SKILL.md may depend on omitted files. Large/data-heavy skills and repositories can exceed the fixed 24-file, 128-KiB/file, 1-MiB-total, 10,000-entry and 2-MiB/tree-response caps; LIMIT is expected and there is no archive/clone/auth fallback. Taste currently has no stable-release observation for the supported check → copy pin → acquire workflow. The API accepts unverified caller-supplied pin labels; it does not enforce that such a label came from check or automatically fall back to a branch.

Selection accepts conservative ASCII paths and rejects secret-like names, including some legitimate `id_mapping` and database filenames. Unselected names may contain spaces or Unicode; a Unicode-fold alias of a selected ASCII name is not detected, but is never written. These path rules do not prove the selected contents are free of secrets or malicious instructions. Acquisition never proves tag-to-commit binding or upstream-history membership, and source licenses/notices must be explicitly selected.

Default Claude, Codex, shared Agents, Gemini, Cursor and Command Code homes are protected by the pilot fence. A live config carves out only its exact named skill folders; the rest of each home stays protected. Existing Claude/Codex environment overrides are recognized; other custom host discovery locations are not discovered automatically and must be declared in `pilot.forbidden`. Native providers, actual host discovery for third-party sources, native adapters, automatic updaters and schedules remain separate work. An incomplete stage is preserved without automatic recovery; see [STORAGE.md](STORAGE.md).

Source installation supports one explicitly mapped text package per stage in disposable Claude `.claude/skills` and Codex `.agents/skills` layouts. It proves no fresh-host discovery, real-source compatibility, twelve-source coverage, legal completeness or runtime dependencies. Unsupported file/metadata shapes are held. Its 256 KiB total cap is lower than acquisition's 1 MiB cap. Scripts are inert 0600 copies, not installed runtimes. Required-file/dependency declarations need user review; link checks cannot discover every dependency.

Missing dependencies, unreviewed selected hosts, legal-target collisions, foreign ownership, competing roots and edits block installation. Names/roots cannot be rewritten in place. A dual-host source installation cannot be updated/removed with a single-host selection while the other copy exists. No adoption, overlay, migration, force or automatic rollback is provided. Restoration requires retained evidence and fresh action approval; interrupted writes stay held for manual review. Existing personal target-home journal matching remains raw-string based; source commands require canonical target homes.

The reciprocal parent checks are conservative. Personal Codex plan/status require existing `.agents` and `.agents/skills` directories to be private even when no same-name copy exists. As a result, a 0755 shared parent returns `PATH_UNSAFE`. Both adapters also block removal when a competing foreign same-name copy exists in another checked root. Neither automatically repairs parent modes or removes competing copies.

The agent hook gets paths from Claude Code tool input. Codex gives patch and command text, so the hook sees Codex edits but not files that Codex reads through the shell. Shell paths are a best-effort guess. On Codex, a `post-tool` lesson arrives after the edit runs. Two hook calls in one session at the same time can both send a lesson, because the session file has no lock. Root matches are exact on real paths, so a root reached through another symlink or a moved checkout does not match. The receipt check trusts files that the same user can change. The stop stub says only where a worktree stood: the branch, the commit and the changed files. The next step comes from a handoff that the agent writes with `handoff write`, and an agent can skip it. The stub names only tracked files; untracked files count but are not named. A repository whose own Git config mentions a filter or an include anywhere, or puts a second section header on one line, gets no stub. A `git status` that takes more than 2 seconds leaves the older stub in place.

The owner-action block is a defense against agents that run devtwin's own hook. It does not stop an agent session that runs without the hook. Examples are a session after the developer removed the entries, and a Codex session that has not trusted them in `/hooks`. It also does not stop an agent that edits the settings files itself. The block reads command text, not a parsed shell command. A command built in a way that the text does not show can pass, and a harmless command can be denied. Previews stay open to agents, so the block must tell a preview from an apply by the `--apply` word. Every lesson and hub owner action therefore also shows the owner dialog, which an agent cannot click.

The organization hub ([HUB.md](HUB.md)) trusts Git push access. Anyone who can push to the hub can add lessons and notes under any handle, and devtwin does not verify the handle or the commit email. `published delete` removes the file and adds a tombstone, but Git history and colleagues' existing clones keep the text. A history rewrite is a manual step for the hub admin, and devtwin does not do it. A tombstone only hides a lesson for clients that honor it. A machine that never synced while the lesson file was there cannot tie a tombstone to the author once the file is gone. That machine never delivered the lesson, but it does not remember the tombstone. The hub sync job is a macOS LaunchAgent; there is no scheduler on other systems. The owner dialog needs a macOS desktop session, so an owner action denies over SSH. A publish that stops between its commit and its outbox write can lose that one item. Hub tests use local bare repositories behind a fixture SSH command; a real SSH host has not been checked.

Lesson replacement ([HUB.md](HUB.md#replace-a-lesson)) checks the remote branch after every fetch, so a second replacement of the same lesson fails with `STALE_VERSION`. Two replacements that were both pushed before either client fetched still both land. devtwin then delivers both as `contested` and keeps the replaced lesson out. It does not choose a winner. The case ends only when the author of one replacement removes it with `published delete`. A held or queued replacement that the sender or the sync drops as stale stays `accepted` in the proposal file; its audit state is `dropped`. The conflict-stop rule is agent judgment, prompted only by the `devtwin-capture` skill until the managed instruction block lands. An agent that does not load that skill gets index lines but no prompt to stop. Replacement notices reach only the author's own machine and only after a `hub sync` there.

The held queue ([HUB.md](HUB.md#held-items)) is a delay, not a review. A lesson nobody cancels leaves after its hold, and the notification shows only on macOS with a desktop session. An item leaves only when `hub sync` or the `learning-send` job runs after its `sendAfter`, so a machine that sleeps sends late. An item whose consent became void stays held until the owner grants the consent again or cancels the item. A send that stops between its push and its audit entry leaves the entry at `held`; `undo` then finds no item and points to `published delete`. An `undo` that loses a race with the sender fails with `STALE_VERSION`, but its own audit entry stays, so the item reads as undone. Repository items have no sender yet and stay held.

"Working on" notes ([HUB.md](HUB.md#working-on-notes)) arrive only when `hub sync` runs, on the poster's machine to push and on the colleague's machine to fetch. With the hub sync job on, that is up to about 20 minutes. A note that waits in the outbox for more than half its 72-hour expiry, for example on a machine that stays offline, is dropped and never posted. The area is a folder guess from the edited paths, not a measure of the change. Notes come only from edit calls that the hook sees: a Codex edit through the shell posts nothing. Each devtwin deletes only its own developer's expired notes, at most 200 per sync. The expired notes of a developer who stops syncing stay in the hub until the admin prunes them. Deleted notes stay in Git history. A hub that holds more than 5000 note files fails to sync with `LIMIT`. Two sessions that replace the same older note at the same time both post; the older file is deleted once. The six-note cap counts per session, and the hook has no lock, so two hook calls in one session at the same time can both post.

Preferences ([AGENT-PROTOCOL.md](AGENT-PROTOCOL.md#9-preferences-and-output-templates)) reach agents only after `instructions apply`. An accepted or retired preference changes nothing in the agent files until you run `instructions plan` and apply it again. The Claude Code block depends on Claude Code reading the `@<path>` import line in `~/.claude/CLAUDE.md`; a path with spaces in it is not a valid import. `pref retire` stops delivery but keeps the record in the personal store. The injection check is a text check: it refuses the common shapes, not every way to phrase an instruction, so the owner dialog is the real review.

## Not covered

These are outside what devtwin does, even when it runs in the background:

- **A lesson line cannot stop a command.** The hook adds guidance to the agent's context. It never returns a deny for a lesson, so a matching command still runs. Rules such as "ask before you push" work only when the agent reads them before it decides.
- **Secrets printed to a terminal.** devtwin does not watch terminal output. The sensitive-text check runs only on text that devtwin stores or sends.
- **Commands that break when pasted.** devtwin does not check or repair shell commands for your shell.
- **Polling long jobs.** devtwin does not watch a job and tell you when it ends.

The tier model ([SECURITY-MODEL.md](SECURITY-MODEL.md#tiers)) trades approval before a write for review after it. You review automatic items in the weekly digest and reverse them with `undo`. The owner dialog of `activity review` answers approve or deny for all of its items, up to ten. To keep some items and drop others, reject the ones to drop with `--reject` first. An item whose full text does not fit one dialog cannot be accepted there; reject it and write it yourself. An agent that writes outside text again in its own words makes an agent write, which only that later review catches. The cap of 20 automatic writes counts each `--session` on its own, and writes with no session in one bucket per caller and UTC day. A caller that passes a new `--session` for each write still stops at 100 automatic writes per UTC day, so that is the real ceiling for one caller label. The command cannot learn the session by itself, and the caller label comes from environment variables. Backups go only to folders inside your home folder, so a copy off the machine needs a folder that a sync service copies.
